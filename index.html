Engineered Reliability

Built around the four failure modes that break migrations

WordPress migration failures are not mysterious accidents. They stem from predictable architectural oversights in legacy plugins. Here is how WP Bundle Migrator solves each one at the engine level.

Failure Mode 01

The server runs out of memory

The legacy flaw: Plugins buffer entire database dumps or gigabyte-scale ZIP archives directly into PHP RAM. On budget or shared hosts with a 128 MB or 256 MB memory limit, the process halts with a fatal "Allowed memory size exhausted" error.
Engineered stream pipeline: Both archive creation and extraction operate in fixed 2 MB chunks via native PHP file handles and buffered HTTP sockets. Memory use remains constant at ~12 MB whether your site is 50 MB or 100 GB.
Failure Mode 02

Domain replacement corrupts serialized data

The legacy flaw: Naive string replacement breaks PHP serialized data structures because string byte counts change. Unserializing to fix it introduces severe CWE-502 PHP Object Injection risks if malicious payloads exist in the database.
Safe tokenizer without unserialize(): A specialized non-executing tokenizer inspects serialized strings, recomputes exact UTF-8 byte lengths (including emojis and multi-byte characters), and rewrites URLs without executing arbitrary PHP code.
Failure Mode 03

The destination server has a newer PHP version

The legacy flaw: Moving an established site from PHP 7.4 to PHP 8.2+ causes immediate fatal syntax errors during WordPress boot due to deprecated functions in neglected third-party plugins, locking you out of wp-admin.
Pre-boot compatibility inspector: Before WordPress boots on the destination, an AST parser verifies plugin code against the target PHP engine. Fatal plugins are deactivated in the database while leaving files intact, producing an actionable audit report.
Failure Mode 04

Gateway timeouts and fragmented downloads

The legacy flaw: Web server reverse proxies (Nginx, Cloudflare, Apache) terminate connections after 60 seconds, leaving 5 GB+ archive downloads corrupted or truncated with "File incomplete" errors.
Resumable downloads via HTTP Range: Full RFC 7233 byte-range support allows downloads to pause, resume, or download across multiple threads via download managers. Output buffers are flushed progressively to prevent server memory bloat.

Developer Automation

Automate everything with WP-CLI

Manage backups and migrations from a terminal, scheduled cron script, or CI/CD pipeline. Complete headless operations with live progress feedback and inline domain rewriting.

  • Instant site replication across development, staging, and production
  • Inline search-and-replace during restore in a single execution
  • Complete vault archive inspection, verification, and pruning 
# 1. Export the entire WordPress site to a compressed bundle
wp bundle export --scope=full

# 2. Turnkey full clone including WordPress core files
wp bundle export --scope=turnkey_full --output=/var/backups/site-clone.zip
# Restore archive and safely rewrite domain across all serialized tables
wp bundle import backup.bundle.zip \
  --old-url="https://dev.local" \
  --new-url="https://production.com"
# Extract subsite #3 from multisite network as a standalone site
wp bundle export \
  --multisite-mode=subsite \
  --subsite-id=3 \
  --convert-standalone
# List all stored backup bundles in the local vault
wp bundle list

# Delete a specific archive bundle
wp bundle delete backup-2026-11-04.bundle.zip

Frequently Asked Questions

Technical answers to common questions about memory handling, serialized data, and server environments.

Why doesn't WP Bundle Migrator crash on hosts with 128 MB memory limits?
Conventional plugins dump the entire database or ZIP file into memory buffers before writing to disk or sending over HTTP. WP Bundle Migrator uses stream handles that operate in fixed 2 MB slices. By continually flushing PHP output buffers and streaming rows incrementally, PHP memory never grows with site size.
How does the URL replacement engine prevent PHP Object Injection (CWE-502)?
Standard search-and-replace scripts often execute PHP's native unserialize() function to parse arrays and objects. If an attacker has inserted a serialized object into post meta or options, unserializing can trigger magic methods (e.g. __wakeup) and remote code execution. WP Bundle Migrator uses a pure tokenizer that parses serialized strings as raw tokens, recalculating string lengths without ever instantiating classes.
Can I extract a single subsite from a WordPress Multisite network?
Yes. With --multisite-mode=subsite --subsite-id=ID --convert-standalone or via the admin UI, WP Bundle Migrator isolates tables prefixed with wp_ID_, copies relevant global users and taxonomy relationships, remaps the prefixes to standalone wp_, and moves the subsite's uploads folder to standard /wp-content/uploads/.
What happens if the destination server runs PHP 8.2+ with legacy plugins?
The built-in pre-boot compatibility inspector examines the plugin files on disk against the destination server's PHP parser before booting WordPress. If fatal syntax errors are discovered, the conflicting plugin is safely deactivated in the database active_plugins array while keeping its files intact, and a conflict report is generated.
Do I need to install the AWS SDK to use Cloudflare R2, Wasabi, or Amazon S3?
No. WP Bundle Migrator has a custom 150-line AWS Signature Version 4 (SigV4) signer written in pure PHP. It performs multipart streaming uploads directly to any S3-compliant API (including MinIO and Google Cloud Storage) without the 30 MB memory and disk footprint of the official AWS SDK.
