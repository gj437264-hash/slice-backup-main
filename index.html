Back up, restore and migrate WordPress without hitting memory or time limits

Slice Backup runs backups and restores as resumable background jobs made of short steps. Closing the browser or a host time limit doesn't lose progress — the next step just picks up where the last one stopped.

Built around the things that break migrations

Most failures come from the same few causes. Each one is handled in the design, not patched afterward.

The server runs out of memory

The problem. Plugins that load a whole archive or table into RAM crash on shared hosting.

Runs as resumable background jobs. Backups and restores are made of short steps (20 seconds by default) that each save their position. Steps are driven by the open admin page, WordPress loopback requests, or WP-Cron, so no single long-running PHP request is needed and an interrupted step resumes instead of restarting.

Changing the domain corrupts data

The problem. Plain search-and-replace breaks serialized PHP strings, and unserializing them to fix it can run attacker-supplied code.

Rewrites URLs without unserialize(). Replacement runs across text columns, handles JSON-escaped URLs and both http:// and https:// variants, and never executes site data — closing the object-injection risk (CWE-502).

The new server has a different PHP version

The problem. Moving to a newer (or older) PHP version can crash the site on incompatible plugin or theme code.

Checks compatibility before the site boots. A plugin that would crash on the destination's PHP version is deactivated (its files are kept); an incompatible active theme falls back to an installed default theme automatically. You get a working site and a report of what changed.

Timeouts and half-finished transfers

The problem. Gateways cut long requests, and large downloads or uploads fail partway through.

Resumable in both directions. Bundles stream to the browser in 2 MB chunks with HTTP Range support, so multi-gigabyte archives can pause, resume, or be fetched with a download manager. Browser uploads are chunked and resumable the same way.

Clean uninstall

Deleting the plugin removes its settings, schedules and temp folders. Backup bundles are kept by default.

Self-healing restores

A conflicting plugin is deactivated with its files kept; a conflicting theme falls back to an installed (or freshly downloaded) default theme automatically, so the site stays up.

Cloud storage, scheduling, transfer and encryption, built in

These modules are part of the core plugin, so there are no add-on ZIPs to install or keep in step with updates. You bring your own storage account — there's no Slice Backup cloud, license key, or storage resale.

Your own cloud storage

Send backups to S3-compatible storage, your SFTP server, or your Dropbox account. The settings screen links to each provider's signup, pricing and key-creation docs.

A built-in SigV4 signer talks to S3 without the AWS SDK; SFTP pins the server's host-key fingerprint; Dropbox uses OAuth 2 PKCE with no app secret stored. Test Connection writes, lists and deletes a file to confirm access before you rely on it.

Scheduled backups

Automatic backups every 12 hours, daily, weekly or monthly, at a time you choose in your site's timezone, with Grandfather-Father-Son retention you configure in days, weeks and months.

Runs on WP-Cron, optionally encrypts and uploads to cloud storage, can delete the local copy after upload, and sends email or JSON webhook alerts (Slack, Discord, Zapier, or any endpoint that accepts a POST). Manual backups are never removed by the retention rule.

Site-to-site transfer

Push a backup to another site, or pull one from it, without downloading the archive to your computer first.

Create a transfer key (valid 1 hour–7 days) on the receiving site, then push from the source or pull from the destination. Every request is authenticated with HMAC-SHA256 over the method, route, body, timestamp and a single-use nonce; keys can be revoked at any time.

Encrypted archives

Protect backups with AES-256-GCM. Every 1 MB chunk is authenticated, so a tampered, reordered or truncated archive fails to restore instead of loading.

Keys come from your passphrase through PBKDF2-SHA256 with 310,000 iterations. Metadata (source site, contents) is encrypted too and only readable with the correct passphrase. Losing the passphrase means the backup cannot be recovered.

  • AES-256-GCM
  • PBKDF2-SHA256, 310,000 iterations
  • 1 MB authenticated chunks

Automate it with WP-CLI

Run exports, restores and transfers from a terminal, a CI job or a headless server — no web server time limits apply. Replace the domain during import in the same command.

Full command reference → 
# Export the whole site
wp slice-backup export

# Turnkey clone with WordPress core, encrypted and uploaded
wp slice-backup export --preset=turnkey_full --encrypt --upload

# Pull subsite #3 out of a network as a standalone site
wp slice-backup export --subsite=3 --standalone

# Restore and swap the domain
wp slice-backup import backup.zip \
  --old-url="https://dev.local" \
  --new-url="https://production.com"

# Import a bundle straight from a public share link
wp slice-backup fetch-link "https://drive.google.com/file/d/XXXX/view?usp=sharing"

# Not happy with the last restore? Undo it.
wp slice-backup rollback undo

# List and delete archives in the local vault
wp slice-backup list
wp slice-backup delete backup.zip

Get started in four steps

  1. Download the plugin .zip from GitHub, or install it from Plugins → Add New → Upload Plugin.
  2. Activate it (network-activate on Multisite), then open Tools > Slice Backup. On Multisite that's Network Admin > Slice Backup.
  3. Create a backup, then restore the bundle on a fresh WordPress install with a different URL to migrate — or set up cloud storage and a schedule under Settings first.
  4. Hit a bug, memory spike or failed restore? Check the FAQ and docs, then report it in GitHub Issues with your PHP version and host.
Good practice: keep a separate backup of any site before you migrate or restore, and try a new setup on staging first. If a restore does go wrong, 1.1.0's safety copy lets you undo it from the Restore tab.
