Getting started

Slice Backup requires WordPress 6.2+ (tested to 7.1) and PHP 7.4+. It is a single plugin with no required add-ons.

Install

  1. Download the plugin .zip, or install it from Plugins → Add New → Upload Plugin.
  2. Activate it. On Multisite, network-activate it instead.
  3. Open Tools > Slice Backup (on Multisite: Network Admin > Slice Backup).
Who can use it. Only administrators can open Slice Backup. On Multisite, only Super Administrators can — every action is also capability-checked and nonce-verified on the backend, so hiding the menu is not the only line of defense.

Moving a whole site

  1. Create a backup on the existing site.
  2. Install WordPress (and Slice Backup) on the destination server.
  3. Upload the backup bundle, or select it from configured cloud storage, pull it from the source site, or paste a share link.
  4. Restore it, replacing the old URL with the new one.

Creating a backup

Choose what to include before you export:

ScopeWhat it includes
Full siteDatabase, uploads, plugins, themes, must-use plugins, languages and root files.
Turnkey cloneEverything in Full site, plus WordPress core itself — useful for a one-file disaster-recovery copy.
Database onlyJust the database tables.
Media onlyJust the uploads folder.
CustomPick any combination of: db, uploads, plugins, themes, mu_plugins, languages, root_files, wp_core.

Optional export filters: skip spam/trashed comments, skip post revisions and trashed posts, and skip cached transients, which reduces archive size without losing real content. A live size estimate is shown before you start.

Every export can also be encrypted, uploaded straight to your cloud storage, or pushed to another site in the same step.

Resumable by design

Backups run as background jobs made of short steps (20 seconds by default). Each step saves its position before it ends, and the next step — triggered by the open admin page, a WordPress loopback request, or WP-Cron — continues from there. You can close the browser without cancelling the job, and a host time limit interrupts a step rather than the whole backup.

Low-traffic sites. WP-Cron is normally triggered by site visits. If your site gets little traffic, point a real server cron job at wp-cron.php (for example every 5 minutes) so scheduled steps and scheduled backups keep running. The System tab warns when a scheduled backup is late.

Restoring & migrating

Upload a bundle (in chunked, resumable pieces, so size isn't limited by your browser or PHP's upload limits), pick it from cloud storage, pull it from another site, or paste a share link — then choose which components to restore.

Domain replacement

Slice Backup replaces the old URL with the new one across text columns in the database without calling unserialize(). A tokenizer recalculates serialized string lengths (including multi-byte UTF-8 and emoji) so serialized PHP arrays and objects stay valid, and it handles both JSON-escaped and plain, http:// and https:// URLs. This avoids the PHP object-injection risk (CWE-502) that comes with unserializing untrusted data.

Table prefix differences

If the backup's table prefix differs from the destination's (for example restoring a multisite subsite as a standalone install), the prefix is rewritten automatically during restore.

PHP compatibility protection

Before activating anything, Slice Backup checks the destination's PHP version against the plugins and theme in the bundle:

  • A plugin that would crash on this PHP version is deactivated in the database (its files are kept, so you can decide what to do with it later).
  • An incompatible active theme falls back to an installed default theme (or downloads one) instead of leaving the site unthemed.
  • Everything that was changed is listed in the restore report.

This is why a restore to a server with a different PHP version typically still leaves you with a working, logged-out-but-browsable site instead of a fatal error.

Damaged archives

If an archive entry can't be read, extraction logs a warning, skips that entry, and restoration continues with everything else instead of aborting the whole restore.

You'll likely be logged out. A database restore replaces users and session data, so existing sessions usually become invalid. Log back in with an account from the restored site once the job finishes — the restore itself keeps running in the background regardless.

Rollback & safety copy New in 1.1.0

Restores are now atomic: the new database and plugin/theme files are staged first, then switched in, while a safety copy of what was there before is kept on disk.

  • If a step crashes partway (out of memory, a host time limit), it's detected and retried in smaller pieces instead of repeating indefinitely or leaving a half-applied restore.
  • After a restore finishes, you can undo it from the Restore tab, or discard the safety copy once you're confident the restore is good.
  • Every restore produces a detailed, downloadable report of what happened and any follow-up action needed (for example, plugins that were deactivated).

From WP-CLI:

wp slice-backup rollback          # shows safety-copy status
wp slice-backup rollback undo     # puts the database, plugins and themes back
wp slice-backup rollback discard  # deletes the safety copy

Import from a share link New in 1.1.0

You can fetch a bundle directly into the backup folder from a publicly-shared link, without downloading it to your computer first. Supported sources:

  • Google Drive (drive.google.com, docs.google.com)
  • OneDrive / SharePoint (1drv.ms, onedrive.live.com, *.sharepoint.com)
  • Dropbox share links
  • Any other direct download URL

The link must have open ("anyone with the link") access. From WP-CLI:

wp slice-backup fetch-link "https://drive.google.com/file/d/XXXX/view?usp=sharing"

The same option is available from the Restore screen in wp-admin.

Multisite

A WordPress Multisite installation can be restored as:

  • An entire network — every site in the network, restored as-is.
  • A single site, converted to standalone — pull one subsite out of the network and turn it into its own single-site WordPress install, with its table prefix rewritten (for example wp_3_posts → wp_posts).
# Export subsite #3 as a standalone bundle
wp slice-backup export --subsite=3 --standalone

Cloud storage

Slice Backup works with storage you already have an account with — there's no proprietary Slice Backup cloud, license key, or storage resale. The settings screen links to each provider's signup, pricing and key-creation pages, and a Test Connection button writes, lists and then deletes a test file so you know access actually works before you rely on it. Large bundles upload in resumable, multi-part pieces.

S3-compatible storage

Amazon S3, Cloudflare R2, Google Cloud Storage (via HMAC keys), Wasabi, Backblaze B2, DigitalOcean Spaces, MinIO, and other S3-compatible endpoints. A small built-in SigV4 signer talks to the API directly, so no AWS SDK is bundled.

SFTP / SSH servers

Password authentication, or private-key authentication with OpenSSH or PEM keys (including passphrase-protected keys). The server's host-key fingerprint is pinned on first connection; if it ever changes, the connection is refused rather than silently trusted, which protects against man-in-the-middle attacks.

Dropbox

Connects to your own Dropbox application using OAuth 2 with PKCE — no app secret is stored, only an encrypted refresh token. Files are written to that application's App folder, not your whole Dropbox. Setup steps are shown directly on the settings screen.

Scheduling & retention

Automate backups on a recurring interval — every 12 hours, daily, weekly, or monthly — at a time you choose in your site's own timezone. A schedule can also:

  • Encrypt the backup and/or upload it to your configured cloud storage automatically.
  • Delete the local copy once the cloud upload succeeds.
  • Email you after every run, or only on failure.
  • POST a JSON summary to a webhook — Slack, Discord, Zapier, or anything that accepts a POST (sent with wp_safe_remote_post(), which blocks requests to internal/private addresses).

Use Run scheduled backup now to test a schedule's settings without waiting for the timer.

Grandfather-Father-Son retention

Configure how many of the newest backups to keep for each of the last N days, N weeks, and N months; older ones are pruned automatically, locally and in cloud storage. Manual backups are never touched by this rule — only backups the schedule itself created.

Site-to-site transfer

Move a backup directly between two WordPress sites without downloading the archive to your computer.

Push (from the source site)

  1. On the receiving site, go to Settings → Site-to-site Transfer and create a transfer key, valid for 1 hour to 7 days.
  2. On the source site, enable Send directly to another site and enter that key.
  3. Optionally, have it restore automatically on the destination once the transfer completes.

Pull (from the destination site)

  1. Go to Restore → From another site.
  2. Enter the source site's transfer key and start the transfer.

Every request is authenticated with HMAC-SHA256 computed over the HTTP method, route, body, a timestamp and a single-use nonce; old, replayed, modified or unsigned requests are rejected. Transfer keys can be revoked at any time.

# From WP-CLI, pull a bundle using a key created on the other site
wp slice-backup pull slicebk1.eyJ1Ijoi...

# Or push while exporting, and restore it on arrival
wp slice-backup export --push=slicebk1.eyJ1Ijoi... --push-restore

Encryption

Backups can be protected with AES-256-GCM. The encryption key is derived from your passphrase with PBKDF2-SHA256, 310,000 iterations, and every 1 MB chunk of the archive is authenticated — so a modified, reordered, or truncated backup fails to restore instead of silently loading corrupted data. Bundle metadata (source site URL, included components) is encrypted too, and only readable once the correct passphrase is entered.

Saved passphrases and cloud secret keys are themselves encrypted using your site's WordPress security keys (AUTH_KEY and friends) and are never stored in plain text. As an alternative to saving the passphrase in the database, define it in wp-config.php:

define( 'SLICE_BACKUP_ENCRYPTION_PASSPHRASE', 'a long random passphrase' );
There is no recovery. If an encrypted backup's passphrase is lost, the backup cannot be decrypted by Slice Backup, its authors, or anyone else. Store the passphrase somewhere safe and separate from the backup itself.

REST API

Slice Backup exposes a REST API under /wp-json/slice-backup/v1/ for headless automation. Authenticate with WordPress Application Passwords (or cookie + nonce from the admin context); every endpoint requires the same capability as the admin screen.

EndpointMethodPurpose
/exportPOSTStart an export job.
/restorePOSTStart a restore job for an uploaded filename.
/backupsGETList stored bundles.
/delete_backupPOSTDelete a stored bundle by file.
/settingsGET / POSTRead or save plugin settings.
/statusGETCurrent job status/progress.

The /peer/* routes power site-to-site transfer. They're HMAC-signed with a transfer key rather than Application Passwords, and aren't meant to be called directly — use the Push/Pull UI or wp slice-backup push/pull/export --push instead.

Security

Access control

  • Only administrators (Super Administrators on Multisite) can use Slice Backup.
  • Every request is capability-checked; applicable requests are nonce-verified.
  • Background processing steps are authorized with a random per-job token.

Backup file protection

  • Bundles get long, random filenames.
  • The temporary backup directory (wp-content/uploads/slice-backup-temp/) is blocked from direct web access on supported Apache and IIS configurations.
  • The System tab tests whether bundles can be downloaded directly over the web, and gives you the rule to add for servers (like Nginx) it can't configure automatically.

Archive security

  • Archives are checked for path traversal / Zip Slip before extraction, on both Linux and Windows path conventions.
  • A wp-config.php found inside a bundle is never applied during restore.

Does Slice Backup send data anywhere?

Only to destinations you explicitly configure: your own cloud storage, your SFTP server, your Dropbox app, another WordPress site you created a transfer key for, your notification email address, or your webhook URL. Slice Backup never sends backup data to its authors.

Uninstalling

Deleting the plugin removes its settings, scheduled tasks, and temporary files. Backup bundles are kept by default, and cloud backups are never deleted automatically. To also delete local bundles on uninstall, add this to wp-config.php before deleting the plugin:

define( 'SLICE_BACKUP_DELETE_BUNDLES_ON_UNINSTALL', true );
